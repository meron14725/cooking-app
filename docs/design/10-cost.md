# 10. 献立の推定金額

買い物リストと提案カードに「だいたいいくらか」を出し、レコメンド v2（[09](./09-recommendation-v2.md)）の点数にも金額を使えるようにします。

1. **買い物リスト**: 今回買う分の合計、1 食あたりの金額、余りの金額（冷蔵庫にある分は買わない分として除く）
2. **提案カード**: 案ごとの推定金額（同じ計算）
3. **レコメンド v2**: 点数の「買い物」の部分に金額を使う
4. **単価**: 食材マスタに価格と出どころ（`default` / `manual`）を持ち、670 件ほどの食材にまとめて目安を入れる（ルール → 残りを AI。`manual` は上書きしない）。食材の編集画面で直せる

## 決まっていること（2026-11-27 ユーザー回答）

| 項目 | 決定 |
|---|---|
| 1 食あたり | 食べる分（冷蔵庫の分を含み、余りを除く）÷ 食数。「今回の支払い ÷ 食数」は並べない |
| 常備品 | 合計に入れず、1 食あたりに固定 20 円（`STAPLE_COST_PER_MEAL_YEN`） |
| 価格の単位 | 食材ごとに代表量あたり 1 つ。まとめ買いの割引は持たない |
| 「約」 | 金額には常に付ける（手入力でも比例計算と 10 円丸めで目安になるため）。未設定があるときは別に「（◯品未設定）」 |
| 古い価格 | 365 日で「古い」と出すだけ。自動の補正はしない |
| 実際の値段から直す | 「買ったチェックで払った金額を入れる」を料金表示の PR の次に入れる。レシートの読み取りはその後で決める |

変えないこと: 買う量は今の `evaluate()`（在庫の割り当て → 販売単位で切り上げ → 余り）で決める。金額は「買う量 × 単価」で後から出すだけで、買い方（どのパックを何個）は金額で変えない。金額の計算は `src/shared/domain/cost.ts` の純粋関数にし、提案と買い物リストで同じものを使う。提案の計算の中で AI は呼ばない。

## 単価の持ち方

### ingredients に足す列（migration 0007）

| 列 | 型 | 内容 |
|---|---|---|
| `price_yen` | integer NULL | **代表量あたり**の価格（円、税込みの目安）。NULL = 価格未設定 |
| `price_source` | text NULL | `default`（まとめて推定で入れた目安）/ `manual`（手で入れた）。`price_yen` が NULL なら NULL |
| `price_updated_at` | text NULL | 価格を入れた日時（ISO）。古さの表示に使う |

- **代表量**は今の `representativeQuantity()` と同じ: 代表の販売単位 → 最初の販売単位 → 基準単位 1 つ分（g なら 100g）。画面では「3個入り あたり 198 円」「100g あたり 128 円」のように、代表量の名前と一緒に見せる
- **単価**（基準単位あたり）= `price_yen ÷ 代表量`。どの販売単位で買っても、量に比例して計算する（「1 個 78 円 / 3 個入り 198 円」のような、まとめ買いの割引は持たない。目安なので割り切る）
- 代表の販売単位を変えたら（例: 3個入り → 1個）、価格は単価が変わらないように換算し直して保存する（`198 → 66`）。出どころと日付はそのまま
- 販売単位ごとに価格を持つ案（`package_units.price_yen`）は、入力の手間が販売単位の数だけ増えるので見送り。割引の差が気になったら後で足せる（列を足すだけで、計算は「その販売単位の価格があればそれ、なければ比例」にできる）
- 09 の `ingredients.attributes_source`（分類・g 換算の出どころ）とは別の列にする。価格だけを手で直すことも、分類だけを直すこともあるため

### 常備品・調味料

| 食材 | 買い物の合計 | 1 食あたり |
|---|---|---|
| 常備品（`is_staple`。塩・しょうゆ・油など） | 入れない（今も買い物リストに出ない） | 定数 `STAPLE_COST_PER_MEAL_YEN = 20` を足し、「調味料など 20 円込み」と書く。0 にすれば消える |
| 常備品でない調味料（オイスターソースなど） | 入れる（実際に買うので） | 使う量の分だけ（大さじ 1 なら大さじ 1 分） |

- 常備品にも価格は入れられるが、合計には使わない（まとめて推定でも常備品は後回しにする）
- 常備品でない調味料は、買ったボトルの大半が余りになる。余りの金額では「傷みやすい余り」と「日持ちする余り」を分けて見せるので、ボトルの余りで見た目が大きくぶれないようにする（下の「余りの金額」）

## 金額の計算

`costOf(evaluation, ingredients, totalMeals)` → `Cost`。提案の案（`Evaluation`）からも、買い物リストの行からも同じ形で出す。

| 値 | 計算 | 画面の言い方 |
|---|---|---|
| `buyYen` | 買う行ごとに `buyQuantity × 単価` の合計 | 今回買う分 |
| `fromFridgeYen` | 在庫から使う量 × 単価の合計（`usesInventory`） | 冷蔵庫から ◯ 円分 |
| `leftoverYen` | 新しく生まれる余り × 単価の合計 | 余り ◯ 円分 |
| `leftoverPerishableYen` | 上のうち、冷蔵のみの食材（`perishable`） | うち傷みやすい ◯ 円 |
| `eatYen` | 料理で使う量 × 単価の合計 = `buyYen − leftoverYen + fromFridgeYen` | — |
| `perMealYen` | `eatYen ÷ 合計食数 + STAPLE_COST_PER_MEAL_YEN` | 1 食あたり |
| `unpricedCount` | 常備品（`is_staple`）を除く、買う・使う食材のうち価格が NULL の食材の数 | （◯ 品未設定） |
| `hasUnpriced` | `unpricedCount > 0` | 未設定の注記を出すか |

- **1 食あたりは「食べる分」で割る**: 買った余りは次の献立に回るので入れず、冷蔵庫から使う分は入れる。こうすると、同じ料理ならいつ作っても 1 食の値段がほぼ同じになる。「今回の支払い ÷ 食数」は、在庫が多い回ほど安く見えてしまうので使わない（確認したいこと 1）
- 金額の前には常に「約」を付ける
- 価格未設定の食材は、どの合計にも入れない（0 円扱い）。そのぶん「（◯ 品未設定）」を出す
- 表示は 10 円単位に丸める（`約 2,380 円`）。合計は丸める前の値で足してから丸める
- 量が「少々」（`quantity = null`）の材料は、今の evaluate と同じく数えない

### 買い物リストで出すとき

買い物リストは確定の後に個数を直したり、手で行を足したりできるので、提案の値ではなく、今の行から計算し直します。

- `buyYen`: 今の行の `buyQuantity × 単価`。手で足した行（`is_manual`）も入れる
- `leftoverYen`: 料理の行だけ `buyQuantity − needQuantity`。手で足した行は「足したかったもの」なので余りにしない
- `fromFridgeYen` と `eatYen`: 献立の料理の材料（`plan_recipes × recipe_ingredients`、食数で倍率）から `eatYen` を出し、`fromFridgeYen = eatYen − 不足量（料理の行の needQuantity）の金額` とする（在庫の確保の表を引き直さない。個数を不足量より減らしても、減らした分は冷蔵庫から使う分に数えない）
- チェックした行・していない行を問わず全部の合計（「今回買う分」）。「あと ◯ 円」（チェックしていない行だけ）も出す
- クエリは今の 3 本（行・販売単位・使い道）に、献立の材料の量を 1 本足す。ID を `IN` に並べない（献立の ID で絞る）

### 提案で出すとき

- `Proposal` に `cost: Cost` を足す。合計食数は案の料理の食数の合計
- 食材マスタはもう全件読んでいるので、列が 3 つ増えるだけでクエリは増えない

## 画面

### 買い物リスト（`ShoppingListView`）

上のまとめに 1 行足す。

- 「3 品は価格未設定」を押すと、その食材の名前の一覧を出し、それぞれ食材の編集へ飛べる
- 行ごとの金額は出さない（リストが混むため）。行を開いたときの詳細に「約 198 円」と出す

### 提案カード

料理の一覧の下（合計の食数の行）に `約 2,380 円 · 1 食 約 410 円` を出す。未設定があれば後ろに小さく `（3 品未設定）`。

### 食材の編集（`IngredientEditPage`）

- 「価格」の欄: `[ 198 ] 円 / 3個入り`（代表量の名前）。下に小さく「目安（自動）· 2026-11-27」または「手入力 · 2026-11-27」
- 値を変えて保存したら `price_source = 'manual'`、`price_updated_at` を今に。空にしたら 3 列とも NULL
- 食材一覧の絞り込みに「価格未設定」「価格が古い」を足す（絞り込みは今は見た目だけなので、この 2 つから動くようにする）

## まとめて推定（09 の流れを使う）

09 の `POST /api/recipes/attributes/estimate` に、価格の段を足します。

1. 食材の分類・g 換算（09）
2. **食材の価格（この設計）**: `price_yen IS NULL` かつ常備品でない食材
3. レシピの区分・系統（09）

返り値に `prices: { updated, remaining }` を足す。1 回の呼び出しでは前の段が残っていればそれだけを進める（09 と同じ）。画面のボタン（09 の「分類をまとめて推定」）は、名前を「分類と価格をまとめて推定」にして、`remaining` が全部 0 になるまで呼び続ける。

### ルール（AI なし）

`src/shared/domain/priceRules.ts` に、よく使う食材の目安を辞書で置く（玉ねぎ 1 個 50 円、豚こま 100g 150 円、木綿豆腐 1 丁 80 円 など、100〜150 件）。

- 食材の名前と別名（`aliases`）で引く。辞書の単位（個・100g・1 丁…）と食材の基準単位が違うときは、`grams_per_unit` で換算できるときだけ使う。換算できなければ AI に回す
- 前の段（食材の g 換算）の AI が残っているあいだは、辞書だけで進め、AI には聞かない（レシピの段も、価格の段が残っているあいだは AI に聞かない）
- 辞書の値は 2026 年の首都圏のスーパーの、特売でない値段の目安。リポジトリに入れてよい（公式レシピのデータではない）
- 入れた値は `price_source = 'default'`

### AI

- ルールで決まらなかった食材を `limit` 件（既定 20）ずつ、名前・基準単位・代表量の名前（例: 「3個入り」「100g」）だけを渡し、`{ id, priceYen }[]` を JSON で受け取る。zod で読み、1〜20,000 円の整数だけを保存する。答えられない食材は NULL のまま（「未設定」に残る）。何度も聞かないよう、`price_updated_at` だけ入れて印にする（対象は `price_yen IS NULL AND price_updated_at IS NULL`。API では価格が NULL なら日付も NULL で返す）。「古い目安を見直す」では、365 日より前の印も消して聞き直す
- provider は [06](./06-ai.md) のもの。670 件なら 34 回前後の呼び出し
- 保存するときは `WHERE price_source IS NULL OR price_source = 'default'` を付け、推定中に手で直された値を上書きしない

### 提案の点数で使う「仮の単価」

価格未設定の食材を 0 円として点数を付けると、未設定の食材を使う案ほど安く見えてしまいます。点数の中だけ、未設定の食材には**同じ分類・同じ基準単位の食材の単価の中央値**を使う（なければ `FALLBACK_PRICE_PER_PACK_YEN = 200` を代表量の価格とみなす。基準単位が違う単価（円/g と円/個）は比べられないので、分類だけの中央値は使わない）。画面に出す金額には使わない（未設定は未設定と出す）。

## レコメンド v2 の点数に金額を使う

09 の式の `shopping` の部分を、価格があるときは金額で数えます。今は「代表量（パック）何個分」で数えているので、`PACK_YEN = 200`（パック 1 個 ≒ 200 円）で金額をパックの数にそろえます。

```
パック換算(食材, 量) = 価格があれば 量 × 単価 / PACK_YEN、なければ 量 / 代表量（今と同じ）

shopping =
    Σ 余り のパック換算 × 傷みやすさ          （今と同じ形。安い食材の余りは軽く、高い食材の余りは重く）
  − Σ 在庫から使う量 のパック換算 × 在庫ボーナス × 期限間近の倍率
  + Σ 期限間近の使い残し のパック換算 × 1.5
  + 買い物点数 × 0.1
  + w.cost × 1 食あたりの買う金額 / 100 円   ← 新しく足す
```

- `w.cost` の初期値は `0.2`（1 食 100 円高いと、冷蔵の余りパック 0.2 個分と同じ）。`RECOMMEND_WEIGHTS` に足し、09 の調整スクリプトで値を変えて見られる
- 新しい項は「1 食あたりの**買う**金額」（`buyYen ÷ 合計食数`）。冷蔵庫の食材を使う案、安い食材の案が上に来る。表示の 1 食あたり（食べる分）とは別の値だが、点数は「今回の出費」を見たいのでこちらにする
- 合計食数は 09 で目標の食数にそろうので、案どうしを同じ条件で比べられる
- 点数の内訳（`scoreBreakdown`）に `cost` を足す
- パック換算（余り・在庫・期限間近の使い残し）は、その食材に価格があるときだけ金額で数える。仮の単価は `cost` の項（買う金額）にだけ使う
- 実装は `src/shared/domain/recommend.ts` の `scorePacks` / `scoreUnitPrices` / `scoreBuyYen`、項は `recommendScore.ts` の `cost`
- 仮の単価の中央値には、削除済みの食材の価格は入れない（削除済みの食材自身の価格は、レシピに残っていれば使う）
- 重みの効き方は `npm run rec:cost`（`--from-local-d1` でローカルの D1）で見る。料理を 1 つずつ食べたい料理にして、重みごとに 1 位の案の買う金額・足した料理の材料費の偏り・1 位の入れ替わりを出す。架空のレシピ 24 件（2026-11-28）では 0.2 で 1 位の入れ替わり 3/24、安い 25% の料理の割合 23% → 27% で、偏りは小さい
- 価格がまだ 1 件も入っていない間は、パック換算は今と同じになり、`cost` の項は仮の単価（200 円 / パック）で効く。まとめて推定が済むまで `w.cost = 0` にしておくかは、調整スクリプトで見て決める

## 価格が古くなったとき

- 自動で値上げ・値下げはしない（物価の補正は持たない）
- `price_updated_at` が `PRICE_STALE_DAYS = 365` 日より前なら、食材の編集に「1 年以上前の価格」と出し、食材一覧の「価格が古い」の絞り込みに出す。買い物リスト・提案の金額は、古くてもそのまま使う（ここでも「約」は常に付ける）
- `default` の価格は、まとめて推定の画面に「古い目安を見直す」を置き、押したときだけ 365 日より前の `default` を NULL に戻して推定し直す（`manual` は触らない）

## レシートや実際の値段から直す

自動の目安は粗いので、1 を料金表示（PR 3）の次に入れます。2 はその後で決めます。

1. **買ったチェックのときに金額を入れる**（小さい）: 買い物リストの行の詳細に「払った金額」の欄。入れたら `price_yen = 払った金額 ÷ 買った量 × 代表量` を `manual` で保存。`shopping_items.paid_yen`（integer NULL）を足し、入れた行は合計にその値を使う（「今回の支払い」が実額に近づく）
2. **レシートの写真から読む**（大きい）: 写真を AI に渡し、品名と金額を食材マスタに当てて、1 と同じ形で保存する。品名の当て方（「国産豚こま切」→ 豚こま切れ肉）と確認画面が要るので、1 を使ってみてから決める

## API の変更（まとめ）

| API | 変更 |
|---|---|
| `GET/PUT /api/ingredients/:id`、`GET /api/ingredients` | `priceYen`・`priceSource`・`priceUpdatedAt` を足す。PUT で `priceYen` が変わったら `manual` と今の日時。省略したら値を残す |
| `GET /api/ingredients` | `?price=missing` / `?price=stale` の絞り込み |
| `GET /api/plans/:id/shopping` | `cost`（上の表の値 ＋ `remainingYen`（あと ◯ 円）＋ `unpriced: { ingredientId, name }[]`。`unpricedCount` と同じく常備品を除く）を足す |
| `POST /api/plans/:id/recommendations` | 各案に `cost` を足す |
| `POST /api/recipes/attributes/estimate` | 価格の段を足し、返り値に `prices: { updated, remaining }`。`{ refreshStalePrices?: boolean }` |

## テストの方針

- **`cost.ts`**（純粋関数）: 単価の比例計算、余りの金額（傷みやすい分を分ける）、冷蔵庫から使う分を買う分に入れない、1 食あたりが食べる分 ÷ 食数 ＋ 常備品の固定費、価格未設定を 0 円にして `unpricedCount` と `hasUnpriced` を返す、常備品は価格が NULL でも `unpricedCount` に数えない、常備品を合計に入れない、10 円単位の丸め
- **代表の販売単位を変えたとき**: 価格が単価を保って換算される
- **買い物リスト**: 個数を直すと `buyYen` が変わる、手で足した行は余りに入らない、チェックしていない行だけの「あと ◯ 円」、100 食材を超える献立でもテスト用 D1（変数 100 で失敗する）で通る
- **まとめて推定**: 辞書で決まる食材・決まらない食材、基準単位が違うときの換算、`manual` を上書きしない（推定中に手で直した場合も）、AI が範囲外の値を返したら捨てる、`refreshStalePrices` で古い `default` だけ戻す
- **点数**: 価格がない食材はパック換算が今と同じ、高い食材の余りほど点数が悪い、`w.cost` を大きくすると安い案が 1 位になる、仮の単価で未設定の食材を使う案が得をしない
