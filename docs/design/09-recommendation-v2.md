# 09. 提案の質を上げる（レコメンド v2）

[05](./05-recommendation.md) の提案を次の 4 点で作り直します。

1. **食数の配分**: 「合計◯食」を目標にし、料理ごとの食数を変えた案も出す（例: カレー 4 食＋副菜 2 食 / カレー 2 食＋副菜 2 品を 2 食ずつ）
2. **案の多様性**: 主な食材・味の系統・加熱のモード・まぜ技・食数の配り方が似た案ばかり並ばないようにする
3. **良さの点数**: 買い物・余り・在庫に加えて、カロリー・野菜・調理時間・ホットクックの回数・人気も見る。重みは定数ファイルで変えられる
4. **「別の案を出す」**（#55/#56）と鍵の固定（別スレッドで作業中）につなげ、回を重ねても新しく、前と似ていない案が出るようにする

変えないこと: ロジックは `src/shared/domain/recommend.ts` の DB に依存しない純粋関数のまま。1 回の評価は今の `evaluate()`（在庫の割り当て → 販売単位で切り上げ → 余り）をそのまま使う。AI は提案の計算の中では呼ばない。

## 決まっていること（2026-11-27 ユーザー回答）

| 項目 | 決定 |
|---|---|
| 食数の目標 | 献立を作るときに「合計◯食」を入れる。既定 6 食（2 人 × 3 日）。前回入れた値を覚える。食べたい料理だけで足りないときは副菜などで埋める |
| 料理の区分 | 主菜 / 副菜 / 汁物 / その他（おやつ・飲み物など）。カレー・丼などのご飯もの・麺は 1 品で主菜を兼ねるので主菜にする（#59・#60 のレビュー） |
| 味の系統 | 和 / 洋 / 中 / エスニック |
| 区分・系統の推定 | 一度まとめて推定して DB に保存し、編集画面で直せる。名前や材料から決まるものは AI を使わない |
| 栄養 | 当面は 1 食あたりのカロリーと野菜の量 |
| 重み | 定数ファイル。値を変えたときの結果を確かめるテストとスクリプトを用意する |
| 食数の刻み | `SERVINGS_STEP = 2`（2 人で食べる前提。定数で 1 に戻せる）。提案カードの ＋－ も同じ刻み |
| 1 品の食数の上限 | `MAX_SERVINGS_PER_DISH = 4`（KN-HW16G は 2〜4 人用）。`max_servings_1_6l` があればその小さいほう。鍵で固定する食数（#58）もこの上限 |
| 日数 | 1 品 = 1 日のまま。品数の上限 `MAX_DISHES = 4` |
| 野菜 | 列は足さず `category = 'vegetable'` を使う。COCORO 取り込みで判定できない食材が vegetable になっているので、まとめて推定で食材マスタの `category` と `grams_per_unit` も直す |
| PR | API と画面を交互に。PR 5 は「点数と配り方」と「絞り込みと多様性」の 2 本。migration はデプロイで本番に自動で入る |
| 規模 | レシピ数百件。絞り込んでから組み合わせる。1 回数百ミリ秒以内。D1 のクエリ回数と変数の上限（100）に注意 |

## 用語

- **食**: 料理 1 食分（今の `servings`）。合計食数 = 献立の料理の `servings` の合計
- **日**: 今と同じく 1 品 = 1 日（1 回作る）。合計日数 = 品数
- **固定（fixed）**: 鍵で固定した料理と食数。別スレッドで `recommend()` に `fixed?: { recipe, servings }[]` を足す（名前は合意済み）。v2 は固定した料理を必ず入れ、食数も変えない

## データ

### recipes に足す列（migration 0008）

| 列 | 型 | 内容 |
|---|---|---|
| `dish_type` | text NULL | `main` / `side` / `soup` / `other`。NULL = 未判定 |
| `cuisine` | text NULL | `japanese` / `western` / `chinese` / `ethnic`。NULL = 未判定 |
| `uses_mixing_unit` | integer NULL | まぜ技ユニットを使うか。NULL = 不明 |
| `cook_minutes` | integer NULL | 調理時間（分、下ごしらえ込みの目安）。NULL = 不明 |
| `attributes_source` | text NULL | `rule` / `ai` / `manual`。上の 4 列をどう決めたか。`manual` は推定で上書きしない |

- 主な食材と加熱のモードは列にせず、提案のたびに材料と `hotcook_mode` から出す（下記「料理の特徴」）。材料を直したら自動で追従させるため
- 野菜かどうかは、食材マスタの `category = 'vegetable'` を使い、列は足さない（ただし手直しが要る。下の「食材マスタの手直し」）。量は g に直して数える（`unit = 'g'` ならそのまま、ほかは `grams_per_unit` を掛ける。`grams_per_unit` がない食材は数えない）
- 画面の「レシピを直す」に区分・系統・まぜ技・調理時間を足す。手で直したら `attributes_source = 'manual'`

### plans に足す列

| 列 | 型 | 内容 |
|---|---|---|
| `target_meals` | integer NULL | 合計◯食の目標。古い献立は NULL |

- 「前回の値」は、いちばん新しい献立の `target_meals`（なければ定数 `DEFAULT_TARGET_MEALS = 6`）。端末をまたいでも同じ値になるよう、ブラウザではなく DB に持つ
- `POST /api/plans` に `targetMeals` を足す。提案の画面で変えたときは `PATCH /api/plans/:id`（draft のみ）で保存してから提案を取り直す
- 献立を作る画面の初期値は `GET /api/plans/defaults` → `{ targetMeals }` で取る（クエリ 1 回）

### ingredients に足す列（migration 0008）

| 列 | 型 | 内容 |
|---|---|---|
| `attributes_source` | text NULL | `rule` / `ai` / `manual`。`category` と `grams_per_unit` をどう決めたか。NULL = 取り込みのまま（未確認）。食材の画面で直したら `manual` |

- `category` に `fruit` は足さない。SQLite は CHECK 制約を変えるのにテーブルの作り直しが要り、ingredients は多くのテーブルから参照されているため。果物は `other` にする（野菜の量には数えない）

### 区分・系統の推定（一度まとめて流す）

1. **ルールで決める（AI なし）**: `src/shared/domain/recipeAttributes.ts` に純粋関数で置く
   - 区分: 名前に「汁・スープ・みそ汁・ポタージュ」→ 汁物。「カレー・丼・ご飯・炊き込み・リゾット・パスタ・うどん」→ 主菜（ご飯もの・麺。「スープカレー」は汁物が先に当たる）。「ケーキ・プリン・ジャム・蒸しパン」→ その他（おやつ）。それ以外は、1 人前の肉・魚・大豆製品・卵が 60g 以上なら主菜、なければ副菜
   - 系統: 名前のキーワード（「中華・麻婆・八宝菜」→ 中、「タイ・ガパオ・グリーンカレー」→ エスニック など）と、材料の調味料（しょうゆ・みりん・だし → 和、コンソメ・トマト缶・バター・チーズ → 洋、豆板醤・オイスターソース・鶏がらスープ → 中、ナンプラー・ココナッツミルク・クミン → エスニック）を数える。いちばん多い系統が 2 位より 2 点以上多いときだけ決める
   - まぜ技: `hotcook_mode` に「まぜる」→ true、「まぜない」→ false。COCORO の `isMixed` があればそれを使う
   - 調理時間: COCORO の `cookingTime`（取り込み時に保存）→ `hotcook_mode` の分数＋下ごしらえの目安 10 分 → NULL
2. **ルールで決まらなかったものだけ AI**: `POST /api/recipes/attributes/estimate`（`{ limit?: number }`、既定 20 件）。未判定のレシピを `limit` 件ずつ、名前と材料の名前だけを 1 回の AI 呼び出しにまとめて渡し、区分と系統を JSON で受け取って保存する（`attributes_source = 'ai'`）。返り値は `{ ingredients: { updated, remaining }, recipes: { updated, remaining } }`。1 回の呼び出しでは食材が残っていれば食材だけ、なくなったらレシピを進める
3. **画面**: レシピ一覧のメニューに「分類をまとめて推定」を置き、`remaining = 0` になるまで呼び続ける（途中で閉じたら止まる。保存済みの分は残る）
4. **食材マスタの手直し**: 同じ API・同じ流れで、`attributes_source` が NULL の食材の `category` と `grams_per_unit` も直す。ルールは名前の辞書（魚・砂糖・かつおぶし・香料・果物・ナッツなど、vegetable に混ざっているもの）と、`unit = 'g'` なら `grams_per_unit` は不要、など。決まらなかったものだけ AI に名前を渡す。`manual` は上書きしない。レシピより先に食材を直す（主菜・副菜の判定が肉・魚の量を使うため）。野菜の点数の重みは、この手直しの後に調整する
5. **新しく足すレシピ**: 保存するときにルールで決め、決まらなかった分は次にまとめて推定するときに入る（取り込みのたびに AI は呼ばない）

AI の入力と出力は [06](./06-ai.md) の provider を使う。AI が区分・系統以外を返しても無視する（zod で読む）。

## 料理の特徴（提案のたびに計算）

`recipeFeatures(recipe, ingredients)` で 1 回だけ計算し、探索中は使い回す。

| 特徴 | 決め方 |
|---|---|
| 主な食材 | 常備品を除いた材料のうち、肉・魚・大豆製品・卵で g 換算がいちばん多いもの。なければ g 換算がいちばん多い材料 |
| 主な食材の分類 | 上の食材の `category`（肉・魚・野菜…） |
| 加熱のモード | `hotcook_mode` のキーワードで `nimono`（煮物）/ `mushi`（蒸し物）/ `muisui`（無水）/ `itame`（炒め）/ `soup`（スープ）/ `other` |
| まぜ技 | `uses_mixing_unit` |
| 1 食あたりの野菜（g） | 野菜の材料の g 換算 ÷ `recipes.servings` |
| 1 食あたりのカロリー | `calories_kcal` |
| 人気 | `log(1 + お気に入り数(favorite_count + is_favorite)) + 0.5 × log(1 + cook_count)` を、候補の中の最大値で割って 0〜1 |
| 必要量のベクトル | 1 食分の食材ごとの必要量（evaluate の手順 1 を前計算） |

## 探索

### 全体の流れ

```
recommend({ anchors, fixed, catalog, available, ingredients, today, targetMeals, exclude, round, weights })
  1. 候補を絞る（数百件 → 30 件前後）
  2. 品数と食数の配り方を作る
  3. 組み合わせ × 配り方を評価して点数を付ける（評価の上限 4,000 回）
  4. 多様性を見ながら 3 案を選ぶ（前に出した案とも比べる）
```

### 1. 候補を絞る

- 外すもの: anchor・固定した料理、削除済み、最小の食数でも 1.6L に収まらないもの
- 残った候補それぞれについて「anchor（今の食数）＋その料理 2 食分」を 1 回だけ評価し、単品の点数（下の式）を出す。評価は候補数ぶん（数百回）で、今の計測では 1 回 30μs 前後なので 20ms 以内
- 次の枠ごとに上位を取り、重複を除いて候補にする（定数 `CANDIDATE_POOL`）

| 枠 | 件数 | 目的 |
|---|---|---|
| 単品の点数が良い | 20 | 食材の使い回し・在庫 |
| 期限間近の在庫を使う | 5 | 冷蔵庫を空ける |
| 人気 | 5 | 定番 |
| 足りない区分（副菜・汁物）ごとの単品上位 | 各 5 | 主菜だけの案にならないように |
| 主な食材が候補に少ないもの | 5 | 多様性の材料を残す |

- 「別の案を出す」の回（`round`、1 回目 = 0）ごとに、枠を 1.5 倍に広げる（上限 60 件）。回を重ねると、1 回目では入らなかった料理まで届く

### 2. 品数と食数の配り方

- 合計食数 `T`（目標）。固定した料理の食数を引いた残りを、残りの料理に配る
- 品数は anchor と固定の数から `MAX_DISHES = 4` まで。追加は最大 3 品
- 1 品の食数は `SERVINGS_STEP`（既定 2）刻みで、`min(MAX_SERVINGS_PER_DISH = 4, max_servings_1_6l)` まで
- `max_servings_1_6l` が刻みより小さい料理（1.6L で 1 食分しか作れないなど）は、追加の候補から外す。anchor や固定にあるときだけ、その値（1 食など）で入れ、合計は「T 以下でいちばん近い」配り方を許す（ぴったりの配り方がないため）
- 合計食数の目標も刻みの倍数にする（画面の ＋－ も 2 刻み）。古い献立の奇数の食数は、刻みの倍数に切り上げて希望として扱う
- anchor の食数も配り直す対象にする（ユーザーの例「カレー 4 食 / カレー 2 食」）。献立を作るときに選んだ食数は「希望」として扱い、離れた分だけ少し減点する（下の `wantDeviation`）。鍵で固定したら変えない
- 合計が `T` にぴったりな配り方だけを作る。anchor の最小の食数の合計だけで `T` を超えるときは、anchor だけの 1 案にする（今と同じ）
- 配り方の数の目安（刻み 2、上限 4）: `T = 6` → 2 品なら [4,2]・[2,4] の 2 通り、3 品なら [2,2,2] の 1 通り。`T = 8` → 2 品 [4,4] / 3 品 3 通り / 4 品 1 通り。刻み 1 に戻すと 3 品で最大 10 通り程度

### 3. 評価する組み合わせの数を抑える

追加品数ごとに、候補の上位から使う件数を変える（定数 `CANDIDATES_BY_ADD_COUNT`）。

| 追加 | 使う候補 | 組み合わせ | × 配り方（T=6） | 評価回数 |
|---|---|---|---|---|
| 0 品 | — | 1 | 〜3 | 〜3 |
| 1 品 | 30 | 30 | 〜3 | 90 |
| 2 品 | 20 | 190 | 〜3 | 570 |
| 3 品 | 10 | 120 | 〜1 | 120 |

- 刻み 2 なら合計 800 回前後。刻み 1 に戻したとき（3,300 回前後）も収まるように、上限は `MAX_EVALUATIONS = 4,000`。上限に達したら、その時点までで選ぶ（単品の点数の良い順に並べてから回すので、良い組み合わせから先に評価される）
- `evaluate()` を速くする: 必要量は前計算したベクトルを食数倍して足すだけにする。`choosePurchase(need, units)` は食材と不足量（小数 3 桁に丸め）で結果を覚えておく（1 回の提案の中だけ）
- 目安: 今の evaluate で 4,000 回 ≒ 130ms。前計算と覚えておく分で 100ms 以下を狙う。D1 のクエリは今と同じ 3 本（食材・販売単位、レシピ・材料、在庫）＋献立 1 本で、件数が増えても回数は変わらない。ID を `IN` に並べるのは献立の料理（最大 10 件）だけ

### 4. 点数（小さいほど良い）

1 案の点数は次の和です。各項目は「パック 1 個分のムダ」くらいの大きさになるように単位をそろえ、重みは `RECOMMEND_WEIGHTS`（`constants.ts`）に置きます。

```
score =
    shopping            今の evaluate の点数（余りのムダ − 在庫ボーナス + 期限間近の使い残し + 買い物点数 × 0.1）
  + w.calorie   × 1 食あたりのカロリーが目標の範囲から外れた分 / 100kcal
  + w.vegetable × 1 食あたりの野菜が目標に足りない分 / 50g
  + w.time      × 調理時間の合計 / 60 分
  + w.hotcook   × ホットクックを回す回数（品ごとに ceil(食数 / 1.6L の上限)）
  + w.repeat    × 同じ料理の食数のうち REPEAT_FREE（2 食）を超えた分
  + w.typeBalance × 区分の偏り
  + w.inPlanSimilarity × 案の中で主な食材・系統が重なった数
  + w.wantDeviation × anchor の食数と希望の食数の差の合計
  − w.popularity × 追加した料理の人気（食数で重み付けした平均、0〜1）
```

- **カロリー**: 1 食あたり = Σ(1 人前のカロリー × 食数) ÷ 合計食数。目標の範囲は `KCAL_PER_MEAL = { min: 450, max: 800 }`。カロリーが分からない料理は計算から外す（分かる料理だけで平均する）
- **野菜**: 1 食あたり = Σ(1 食あたりの野菜 × 食数) ÷ 合計食数。目標は `VEGETABLE_G_PER_MEAL = 120`（1 日 350g の 1/3 の目安）。多い分は加点しない
- **区分の偏り**: 主菜の食数が合計の 1/3 未満なら 1、汁物・その他だけで半分を超えたら 1（足し算）。未判定の料理は数えない。カレー・丼などは主菜なので、「カレー 4 ＋副菜 2」の偏りは 0
- **案の中の重なり**: 同じ主な食材の料理が 2 品以上あるとき 1 品ごとに 1、同じ系統が 3 品以上なら 1。使い回しで買い物が減る分と引き合う（重みで調整）
- 点数の内訳（項目ごとの値）を `Proposal.scoreBreakdown` として返す。調整のスクリプトとテストで使い、画面には今は出さない

重みの初期値（実際に使って調整する）:

| 重み | 初期値 | 意味 |
|---|---|---|
| `calorie` | 0.3 | 100kcal 外れるとパック 0.3 個分のムダと同じ |
| `vegetable` | 0.3 | 50g 足りないと 0.3 |
| `time` | 0.2 | 60 分で 0.2 |
| `hotcook` | 0.1 | 1 回で 0.1 |
| `repeat` | 0.3 | 2 食を超えた 1 食ごとに 0.3（カレー 4 食で 0.6） |
| `typeBalance` | 0.5 | |
| `inPlanSimilarity` | 0.2 | |
| `wantDeviation` | 0.1 | 希望から 1 食ずれるごとに 0.1 |
| `popularity` | 0.5 | いちばん人気の料理で −0.5 |

### 5. 多様性を見ながら 3 案を選ぶ

点数順の一覧から、次の値がいちばん小さい案を 1 つずつ選びます（MMR と呼ばれる方法）。

```
選ぶ値 = score + DIVERSITY_LAMBDA × max(similarity(案, 選んだ案と前に出した案))
```

- `DIVERSITY_LAMBDA = 1.0`。大きくすると点数より違いを優先する
- **前に出した案**（`exclude`）も比べる相手に入れる。「別の案を出す」を押すたびに、前に見た案と似ていない案が上に来る
- 同じ料理と同じ食数の案（前に出したものを含む）は選ばない

**似ている度合い** `similarity(a, b)`（0〜1）: anchor と固定を除いた「追加した料理」と食数の配り方で比べ、次の重み付き平均を取ります。

| 特徴 | 重み | 比べ方 |
|---|---|---|
| 追加した料理 | 0.35 | レシピ ID の重なり（Jaccard） |
| 主な食材 | 0.2 | 主な食材の重なり（Jaccard） |
| 主菜の系統 | 0.15 | 同じなら 1 |
| 加熱のモード | 0.1 | モードの集合の重なり |
| まぜ技 | 0.05 | 使う品数が同じなら 1 |
| 食数の配り方 | 0.15 | 食数を大きい順に並べた形が同じなら 1（例: [4, 2] と [4, 2]） |

- 重みは `SIMILARITY_WEIGHTS`（`constants.ts`）
- 追加した料理がない案（anchor だけ）どうしは、食数の配り方だけで比べる

## 「別の案を出す」と鍵の固定

### exclude の形を変える

v2 では同じ料理でも食数が違えば別の案なので、`exclude` に食数を含めます。

```ts
// 今
exclude?: string[][]
// v2
exclude?: { recipeId: string; servings: number }[][]
```

- 古い形（文字列の配列）も受け付ける（`sessionStorage` に古い形が残っている端末のため）。その場合は食数を問わずに、その料理の組み合わせを除く（今と同じ動き）
- 比べるキーは「anchor と固定を除いた、追加した料理と食数」。anchor の食数を配り直した案は、anchor の食数も含めて比べる
- `round` は `exclude` から出す（何回目かは画面が持たない）。`round = ceil(exclude の案の数 / maxProposals)`
- `hasMore`: 今回の候補（広げた枠）の中に、まだ出していない組み合わせが残っているか。枠をこれ以上広げられず、残りもなければ false
- 上限: `exclude` は今の 300 案のまま。食数付きで 1 案 4 品（`MAX_DISHES`）× 300 = 1,200 要素で、JSON で 40KB 程度（D1 には渡さない）

### 鍵の固定

- 別スレッドの設計のまま `fixed?: { recipe, servings }[]`（API は `{ recipeId, servings }[]`）を受け取る。v2 では、固定した料理の食数を合計食数から引いて残りを配る
- 固定を変えたら画面は `exclude` を空にして 1 回目から（別スレッドの設計どおり）
- 鍵の PR が先に入った場合は、v2 の探索をその上に乗せる。v2 が先なら、鍵の PR は `fixed` を渡すだけになる

## AI を使う部分と使わない部分

| 部分 | AI | 理由 |
|---|---|---|
| 提案の計算（絞り込み・配り方・点数・多様性） | 使わない | 毎回すぐ返す、同じ入力なら同じ結果、費用ゼロ |
| 区分・系統の推定 | ルールで決まらなかったときだけ、まとめて一度 | 結果を DB に保存するので、提案のたびには呼ばない |
| 余りを使う 1 品の提案（今の AI 補完） | 押したときだけ | 今と同じ。すすめる条件に「足りない区分（副菜・汁物）の候補が 0 件」を足す |

## 重みを確かめる道具

- **スクリプト** `npm run rec:try -- [--weights weights.json] [--target 6] [--anchor <レシピ名>]`（`scripts/recommend-playground.ts`）: テスト用の献立データ（下記）で `recommend()` を回し、案ごとに料理・食数・点数の内訳を表に出す。`--weights` で一部の重みだけ上書きし、既定の重みとの違い（順位が変わった案）も出す
- **本番に近いデータで試す**: `--from-local-d1` で `wrangler d1 execute --local` のデータを読む。公式レシピの本文や写真はリポジトリに入れない方針なので、手元の D1 から読むだけにする

## テストの方針

`src/shared/domain/recommend.test.ts` に足す（純粋関数なので DB なし）。テスト用の献立データは `src/shared/domain/testing/catalog.ts` に、seed のレシピをもとにした架空の 30 件程度を置く（公式レシピは使わない）。

- **食数**: 案の食数の合計が必ず目標と同じ。どの料理の食数も刻みの倍数で `MAX_SERVINGS_PER_DISH` と 1.6L の上限以下。固定した料理の食数は変わらない。anchor の最小の食数だけで目標を超えたら anchor だけの 1 案
- **配り方の案が出る**: カレー（anchor）と副菜の候補で、目標 6 食のとき「カレー 4 ＋副菜 2」と「カレー 2 ＋副菜 2 ＋副菜 2」の両方が 3 案の中に入る（重みの初期値で）。「カレー 4 ＋副菜 2」の `typeBalance` は 0
- **作れる量が刻みより小さい料理**: 1.6L で 1 食しか作れない料理は追加の候補に出ない。anchor にあるときは、合計が T 以下でいちばん近い配り方になる
- **点数の各項目**: 項目ごとに、その項目だけが違う 2 案を作り、向きが正しいことを確かめる（野菜が多い案が上、人気の料理が上、カロリーが範囲内の案が上 など）
- **重みを変えると結果が変わる**: `popularity` を大きくすると人気の料理が 1 位になる、`repeat` を 0 にするとカレー 6 食の案が出る、など。重みの調整で効き方が壊れていないかを見る
- **多様性**: 候補が十分あるとき、3 案の主な食材がすべて同じにならない。`DIVERSITY_LAMBDA = 0` にすると点数順そのままになる
- **別の案を出す**: 5 回続けて `exclude` を足していくと、同じ料理と食数の案は二度出ない。2 回目の案は 1 回目の案と似ている度合いが一定以下。出し尽くすと `proposals: []`・`hasMore: false`。古い形の `exclude` も受け付ける
- **計算量**: 架空の 500 件で、評価回数が `MAX_EVALUATIONS` 以下（評価回数を数えるカウンタを返すか注入する）。時間は CI で揺れるので、時間の検査は「2 秒以内」のゆるい確認だけ
- **区分・系統のルール**: 名前と材料の例で、決まるもの・決まらないもの（NULL）を確かめる。`manual` は上書きしない
- **API**: `plans.node.test.ts` に、`targetMeals` の保存と前回の値、`exclude` の新旧の形、テスト用 D1（変数 100 で失敗する）で 300 件のレシピでも通ること
- **画面**: 合計◯食の入力（初期値が前回の値、変えると提案を取り直す）、「別の案を出す」で食数付きの `exclude` を送ること
