# 05. レコメンド

目指すのは「食べたい料理が入っていて、買ったパックを食べ切れ、下ごしらえが 1 回で済む組み合わせ」です。在庫（前回の余りや期限間近のもの）は積極的に使います。カロリーは表示だけで、提案の除外や減点には使いません。

ロジックは `src/shared/domain/recommend.ts` に DB に依存しない純粋関数として実装し、単体テストで挙動を固めます。

## 入力と出力

```ts
recommend({
  anchors: { recipe: Recipe, servings: number }[],  // 食べたくて選んだ料理と食数
  catalog: Recipe[],             // 登録レシピ全部（材料つき）
  available: AvailableStock[],   // 使える在庫（確保分を引いた量、行ごとの期限つき）
  ingredients: Map<id, Ingredient & { packageUnits }>,
  today: string,                 // todayJst() で作った日付
  options: { targetCount: 3, maxProposals: 3, defaultServings: 1 },
}) => { proposals: Proposal[], aiSuggestionRecommended: boolean }
```

`available` は「在庫 − `stored` の袋の `before_cook` 確保分」です（[02](./02-data-model.md) の在庫の動き）。確保済みの豆腐を次の献立に二重に割り当てないためです。

## 1つの組み合わせの評価

組み合わせ（料理と食数の集合）を受け取って、買い物と余りを計算する関数 `evaluate(items)` を中心に置きます。

### 手順

1. **必要量を集計**: 料理の材料を `係数 = 食数 / recipes.servings` でスケールし、食材ごとに合計する。`quantity = NULL`（少々）と常備品（`is_staple`）は計算から外す
2. **在庫を割り当て**: 食材ごとに、使える在庫を期限の近い順に割り当てる。足りない分が不足量
3. **販売単位で切り上げ**: 不足量を満たす買い方を選ぶ（下記）
4. **新しく生まれる余りを出す**: `余り = 買った量 − 不足量`（0 以上）。割り当てなかった在庫は「元からある在庫」なので余りに数えない
5. **スコアを付ける**（下記）

### 販売単位の選び方

食材ごとに販売単位の組み合わせから「不足量以上で、余りが最小、同じなら買う個数が最小」を選びます。販売単位は 1 食材あたり 1〜3 種類程度なので、各単位 0〜(不足量/量+1) 個の全探索で十分です。

例: 玉ねぎが 2 個不足、販売単位が「1個売り」「3個入り」
- 1個売り × 2 → 余り 0（買う個数 2）
- 3個入り × 1 → 余り 1
→ 1個売り × 2 を選ぶ

販売単位が登録されていない食材は、不足量ぴったりを買う（量り売り扱い）。

### スコア（小さいほどよい）

```
score =
    Σ 新しく生まれる余りのムダ
  − Σ 在庫を使ったボーナス
  + Σ 期限間近の在庫を使い残したペナルティ
  + 買い物点数 × 0.1

余りのムダ        = (余り量 / 代表量) × 傷みやすさ
在庫を使ったボーナス = (使った在庫量 / 代表量) × 0.5（期限間近の在庫なら × 1.5）
期限間近ペナルティ  = (期限間近の在庫のうち使わなかった量 / 代表量) × 1.5
```

**代表量**（単位の違いを吸収するための分母）は次の順で決める。

1. `is_default = 1` の販売単位の量
2. なければ、最初に登録された販売単位の量
3. それもなければ、基準単位 1 つ分（g の食材なら 100g とみなす）

**傷みやすさ**は次の順に判定し、最初に当てはまったものを使う。

1. 常温で日持ちする（`pantry_days ≥ 30`。玉ねぎ、じゃがいもなど）→ 0.1
2. 冷凍できる（`can_freeze = 1`）→ 0.3
3. それ以外（冷蔵のみ。葉物、豆腐など）→ 1.0

- 余りを「代表的なパックの何割が余るか」で正規化するので、g と個のような単位の違いを吸収できる
- 在庫を使う案は、使わない案よりスコアが良くなる（前回の余りを次回で使う、という要件の中心）
- 重みは初期値で、実際に使って調整する（`shared/domain/constants.ts` にまとめる）

## 組み合わせの探索

目標は anchor を含めて `targetCount`（3）品。追加する品数は `targetCount − anchors.length`。追加料理の食数は `defaultServings`。

1. **候補**: catalog から anchor を除き、1.6L に収まらないもの（下記）を除いたレシピすべて
2. **全探索**: 候補から追加品数ぶん選ぶ組み合わせをすべて evaluate する。登録レシピが数十件のうちは十分速い（60 件・2 品追加でも 1,770 通り、1 回の evaluate は食材数十個の足し算）
3. **似た案を避けて上位を選ぶ**: スコア順に見て、すでに選んだ案と追加料理が 1 品でも同じなら飛ばす。それで `maxProposals` 件に届かなければ、飛ばした案から順に埋める
   - 「別の案を出す」: `exclude` に入った組み合わせ（anchor を除いた追加料理の集合で比べる）を先に除いてから同じ手順で選ぶ。残りがなければ `proposals: []`、選んだ後にまだ残っていれば `hasMore: true`
4. anchor だけで 3 品以上ある場合は探索せず、anchor のみを 1 案として返す

登録レシピが 100 件を超えて遅くなったら、「単品追加でのスコア改善が大きい上位 K 件に絞ってから全探索」を足す（計測してから）。

## 1.6L の制約

- `max_servings_1_6l` があるレシピは、その献立での食数がそれ以下のときだけ候補にする
- NULL（不明）のレシピは候補に含め、提案カードに「1.6L に収まるか未確認」と出す
- URL 取り込み・AI 提案のときに AI に推定させ、本人が確認する（[06](./06-ai.md)）
- 3 品は別々の日に 1 品ずつ作るので、組み合わせ全体の容量は制約にしない

## 食べる順の初期値

確定時（S03）に `day_index` の初期値を決めます。本人は並べ替えで変えられます。

1. 各料理について、使う食材（packed になるもの）の「切った後の冷蔵日持ち」の最小値を出す
2. それが短い料理、冷凍できない食材が多い料理を先（1日目）にする
3. anchor（食べたくて選んだ料理）は同点なら先

## AI 補完の判断

次のどちらかなら `aiSuggestionRecommended = true` にし、画面に「余る食材で AI に 1 品提案してもらう」を出します。

- 追加料理の候補が 0 件（登録レシピが少ない）
- 最良案でも「冷蔵のみの食材の余り」が代表量の 0.5 パック分以上残る

AI の提案は下書き（RecipeDraft）として返り、本人が確認して保存すると catalog に入るので、もう一度レコメンドを回すと案に含まれます（[06](./06-ai.md)）。AI を自動で呼ぶことはしません（費用と待ち時間のため）。

## 要件定義の流れとの対応

| 要件定義の手順 | 設計 |
|---|---|
| 1. 起点の料理に必要な食材を集計 | evaluate 手順1（食数でスケール） |
| 2. 在庫を引く（余り・期限間近を優先） | evaluate 手順2、在庫ボーナス、期限間近ペナルティ |
| 3. 販売単位で切り上げ | 販売単位の選び方 |
| 4. 切り上げで余る食材を見る | evaluate 手順4 |
| 5. 余りを活かす追加料理を探す。なければ AI | 探索、AI 補完の判断 |
| 6. 追加料理で買い物が増えたら集計からやり直す | 組み合わせごとに evaluate を最初から計算 |
| 7. 約3品、余分が少ない、1.6L | targetCount、スコア、1.6L の制約 |
| 8. 余りは在庫に残して次回優先 | 在庫の動き（[02](./02-data-model.md)）、在庫ボーナス |

## テストケース（抜粋）

- 玉ねぎ 3個入りしかないとき、玉ねぎを 1 個使う料理を追加する案が上位に来る
- **期限が先の在庫を使う案が、その在庫を使わない案より上位に来る**
- 期限間近の在庫を使う料理が、使わない料理より上位に来る
- 在庫で足りる食材は買い物リストに出ない
- `stored` の袋が確保している在庫は割り当てられない
- 2 人前のレシピを 1 食分で入れると、必要量が半分になる
- 少々・常備品は買い物リストにも余りにも出ない
- 販売単位がない食材は不足量ぴったりで買い、ムダは 0
- 販売単位がない食材でもムダの計算で 0 除算にならない
- anchor が 3 品のときは探索しない
- 食数が `max_servings_1_6l` を超えるレシピは提案に出ない
- 上位 3 案で追加料理が重ならない（候補が十分あるとき）
- `exclude` に渡した組み合わせは返さない。出し尽くすと空で `hasMore: false`

## 下ごしらえの集約

`src/shared/domain/prep.ts` に純粋関数で置きます。袋の保存場所（[02](./02-data-model.md)）が決まっていることが前提です。

1. 献立の材料（スケール後）を、袋ごとに次のどれかに分ける
   - `before_cook_task` がある食材 → 切らずに残す（作業内容はマスタの値）
   - 冷凍の袋で `can_freeze = 0` の食材 → 切らずに残す（「冷凍できないので直前に切る」）
   - それ以外で `cut_style` がある → 今切る
   - `cut_style` がない → そのまま袋へ
2. 「今切る」ものを食材ごとにまとめ、料理ごとの切り方と量を並べる
3. 並び順は売り場順（野菜 → 肉 → 魚 …）。まな板を汚す肉・魚を後にするため
