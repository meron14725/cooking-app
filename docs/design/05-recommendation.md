# 05. レコメンド

目指すのは「食べたい料理が入っていて、買ったパックを食べ切れ、下ごしらえが 1 回で済む組み合わせ」です。カロリーは表示だけで、提案の除外や減点には使いません。

ロジックは `src/shared/domain/recommend.ts` に DB に依存しない純粋関数として実装し、単体テストで挙動を固めます。

## 入力と出力

```ts
recommend({
  anchors: Recipe[],             // 食べたくて選んだ料理（1品以上）
  catalog: Recipe[],             // 登録レシピ全部（材料つき、fits_1_6l=1 のもの）
  inventory: InventoryItem[],    // 現在の在庫
  ingredients: Map<id, Ingredient & { packageUnits }>,
  today: string,
  options: { targetCount: 3, maxProposals: 3, expiringSoonDays: 2 },
}) => { proposals: Proposal[], aiSuggestionRecommended: boolean }
```

## 1つの組み合わせの評価

組み合わせ（料理の集合）を 1 つ受け取って、買い物と余りを計算する関数 `evaluate(recipes)` を中心に置きます。

### 手順

1. **必要量を集計**: 料理の材料を食材ごとに合計する。`quantity = NULL`（少々）と常備品（`is_staple`）は計算から外す
2. **在庫を引く**: 食材ごとに、在庫を期限の近い順に割り当てる。足りない分が不足量
3. **販売単位で切り上げ**: 不足量を満たす買い方を選ぶ（下記）
4. **余りを出す**: 余り = 割り当て後の在庫残り + 買った量 − 不足量
5. **スコアを付ける**（下記）

### 販売単位の選び方

食材ごとに販売単位の組み合わせから「不足量以上で、余りが最小、同じなら買う個数が最小」を選びます。販売単位は 1 食材あたり 1〜3 種類程度なので、各単位 0〜(不足量/量+1) 個の全探索で十分です。

例: 玉ねぎが 2 個不足、販売単位が「1個売り」「3個入り」
- 1個売り × 2 → 余り 0（買う個数 2）
- 3個入り × 1 → 余り 1
→ 1個売り × 2 を選ぶ

販売単位が登録されていない食材は、不足量ぴったりを買う（量り売り扱い）。

### スコア（小さいほどよい）

```
score =
    Σ 余り食材の「ムダ」
  + Σ 期限間近の在庫を使い残したペナルティ
  + 買い物点数 × 0.1

余り食材のムダ   = (余り量 / その食材の代表的な販売単位の量) × 傷みやすさ
傷みやすさ       = 冷凍できる → 0.3、冷蔵のみ → 1.0、常温で日持ちする（pantry_days ≥ 30）→ 0.1
期限間近ペナルティ = 期限間近（expiringSoonDays 以内）の在庫で、この組み合わせで使われない量 / 販売単位 × 1.5
```

- 余りを「パックの何割が余るか」で正規化するので、g と個のような単位の違いを吸収できる
- 冷凍できる食材の余りは次回に回せるので軽く、冷蔵のみの葉物などは重くする
- 重みは初期値で、実際に使って調整する（定数として 1 か所にまとめる）

## 組み合わせの探索

目標は anchor を含めて `targetCount`（3）品。追加する品数は `targetCount − anchors.length`。

1. **候補の絞り込み**: catalog から anchor を除いたレシピそれぞれについて、`anchors + そのレシピ` を evaluate し、単品追加でのスコア改善が大きい順に上位 K=15 件を候補にする。改善の指標は「anchor の余りを使える量」と「期限間近の在庫を使える量」
2. **全探索**: 候補から追加品数ぶん選ぶ組み合わせをすべて evaluate する（K=15、2品追加で 105 通り。十分速い）
3. **上位 maxProposals 件**を返す。似た案ばかりにならないよう、追加料理が完全に同じ案は除く
4. anchor だけで 3 品以上ある場合は探索せず、anchor のみを 1 案として返す

レシピが数百件に増えても、1 の絞り込みが O(N) なので 1 秒以内に収まる想定です。

## 1.6L の制約

- レシピ単位で `fits_1_6l` を持ち、1 の時点で 0 のものを除く
- 3 品は別々の日に 1 品ずつ作るので、組み合わせ全体の容量は制約にしない

## AI 補完の判断

次のどちらかなら `aiSuggestionRecommended = true` にし、画面に「余る食材で AI に 1 品提案してもらう」を出します。

- 登録レシピが少なく、追加料理の候補が 0 件
- 最良案でも「冷蔵のみの食材の余り」が販売単位の 0.5 パック分以上残る

AI の提案は下書き（RecipeDraft）として返り、本人が確認して保存すると catalog に入るので、もう一度レコメンドを回すと案に含まれます（[06](./06-ai.md)）。AI を自動で呼ぶことはしません（費用と待ち時間のため）。

## 要件定義の流れとの対応

| 要件定義の手順 | 設計 |
|---|---|
| 1. 起点の料理に必要な食材を集計 | evaluate 手順1 |
| 2. 在庫を引く（余り・期限間近を優先） | evaluate 手順2、期限間近ペナルティ |
| 3. 販売単位で切り上げ | 販売単位の選び方 |
| 4. 切り上げで余る食材を見る | evaluate 手順4 |
| 5. 余りを活かす追加料理を探す。なければ AI | 探索の 1〜2、AI 補完の判断 |
| 6. 追加料理で買い物が増えたら集計からやり直す | 組み合わせごとに evaluate を最初から計算 |
| 7. 約3品、余分が少ない、1.6L | targetCount、スコア、fits_1_6l |
| 8. 余りは在庫に残して次回優先 | 在庫の動き（[02](./02-data-model.md)）、期限間近ペナルティ |

## テストケース（抜粋）

- 玉ねぎ 3個入りしかないとき、玉ねぎを 1 個使う料理を追加する案が上位に来る
- 期限間近の在庫を使う料理が、使わない料理より上位に来る
- 在庫で足りる食材は買い物リストに出ない
- 少々・常備品は買い物リストにも余りにも出ない
- 販売単位がない食材は不足量ぴったりで買う
- anchor が 3 品のときは探索しない
- fits_1_6l = 0 のレシピは提案に出ない

## 下ごしらえの集約

レコメンドと同じく `src/shared/domain/prep.ts` に純粋関数で置きます。

1. 献立の材料を `cut_timing` で分ける
2. `prep` のものを食材ごとにまとめ、料理ごとの切り方と量を並べる
3. `before_cook` のものは「切らずに残す」に、理由（マスタの `cut_before_cook_note`）と料理名を付ける
4. 並び順は売り場順（野菜 → 肉 → 魚 …）。まな板を汚す肉・魚を後にするため
