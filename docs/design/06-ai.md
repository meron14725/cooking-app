# 06. AI 連携

> 2026-11-27: AI は Cursor SDK（Cloudflare Containers）に移し、言葉でデータを変える「AI に頼む」を足すことになりました。構成と、AI に渡す範囲の変更は [08](./08-agent.md) にあります。この文書の Gemini の記述は予備のプロバイダとして残します。

AI は次の 3 か所と、[08](./08-agent.md) の「AI に頼む」で使います。どれも結果は下書きで、本人が確認してから保存します。

| 用途 | 入力 | 出力 |
|---|---|---|
| URL 取り込み | レシピページの本文 | RecipeDraft |
| 補完レシピ提案 | 余りそうな食材、既存レシピ名（重複回避） | RecipeDraft |
| カロリー推定 | レシピの材料と人数 | 1 人前のカロリー |

## プロバイダの分離

```ts
// src/server/ai/provider.ts
type MasterRef = { name: string; unit: string; gramsPerUnit?: number }  // 食材マスタの名前と基準単位

export interface AiProvider {
  extractRecipe(input: { url: string; text: string; ingredients: MasterRef[] }): Promise<RecipeDraftRaw>
  suggestRecipe(input: {
    leftovers: { name: string; quantity: number; unit: string }[]
    avoidTitles: string[]
    ingredients: MasterRef[]
  }): Promise<RecipeDraftRaw>
  estimateCalories(input: {
    servings: number
    ingredients: { displayText: string }[]
  }): Promise<{ caloriesKcal: number }>
}
```

- 実装は `src/server/ai/<provider>.ts` に 1 ファイルずつ置き、環境変数 `AI_PROVIDER` で切り替える
- どのプロバイダでも「JSON スキーマに沿った構造化出力」を使い、返ってきた JSON を zod で検証する。検証に失敗したら 1 回だけ再試行し、だめなら 502
- テスト用に固定値を返す `FakeProvider` を用意する
- MVP ではプロバイダを 1 つに決めて実装する。構造化出力が使えて、安くて速いモデル（Claude の Haiku 系、Gemini の Flash 系など）を想定
- 実装（#6）: Gemini Flash 系で実装した（`src/server/ai/gemini.ts`、確認中。[README](./README.md) の未決事項）。`AI_PROVIDER` は `gemini`（既定）か `fake`
  - 構造化出力には zod から作った JSON スキーマを渡す。範囲や長さの制約が多いと Gemini が受け付けないので、渡すスキーマからは制約を外し、返ってきた JSON を zod で検証するときに見る
  - タイムアウトは AI 1 回 9 秒。ページ取得（リダイレクト込みで 10 秒）+ AI 9 秒 × 2 回 = 28 秒で、画面の 30 秒に収める
- ページの取得: http(s) だけ。localhost やプライベート IP は断る。リダイレクトは自分で 3 回までたどり、行き先ごとに同じ確認をする。文字コードは Content-Type か `<meta charset>` で決める（Shift_JIS のサイト対策）
- マスタと照合できなかった材料は、下書きに候補名と単位（`suggestedName`、`suggestedUnit`）を残し、量もその単位のまま返す。画面でマスタに追加すると、その食材を選んだ状態になる

## URL 取り込みの流れ

「＋」のパネルに URL を貼ると `POST /api/recipes/draft` がこの流れで下書きを作る（URL 以外の文はメモとして AI に渡す）。COCORO KITCHEN の URL だけは、ページではなくレシピ 1 件の JSON を取り、メモがなければ AI を使わずに下書きを組み立てる（[04](./04-api.md)）。

1. Worker がページを `fetch`（タイムアウト 10 秒、サイズ上限 2MB）
2. **構造化データを先に見る**: `<script type="application/ld+json">` に schema.org の `Recipe` があれば、材料と手順をそこから取る。多くのレシピサイトが持っている
3. 構造化データがなければ、HTML からタグを除いた本文（上限 2 万文字程度）を AI に渡して抽出
4. どちらの場合も、AI に次を依頼する
   - 材料を食材マスタの名前に寄せる。なければ新規候補名
   - 量をマスタの基準単位に直す（「1/2個」→ 0.5、`gramsPerUnit` があれば「玉ねぎ 150g」→ 0.75個）。直せなければ元の単位のまま返す
   - 手順を下ごしらえ（prep）と調理（cook）に分ける
   - ホットクックの手順・設定に直す（元が鍋のレシピの場合）。直したことは `warnings` に書く
   - 1.6L 機で作れる最大の人数分（`maxServings1_6l`）を推定する
5. サーバ側で別名（`aliases`）による照合をもう一度行い、`ingredientId` を埋める。単位はサーバ側で最終判定する（[04](./04-api.md) の単位の扱い）
6. 画面で確認・修正。マスタにない食材は、その場で食材マスタに追加できる

大量取得はしない（1 回の操作で 1 URL だけ取りに行く）。

## 補完レシピ提案の流れ

1. レコメンド画面で「余る食材で AI に 1 品提案してもらう」を押す
2. 余りそうな食材（冷蔵のみを優先）を渡し、「ホットクック 1.6L で作れる、成人男性 1 人前、600kcal 前後を目安」の条件で 1 品出してもらう
3. 下書きを確認して保存 → レコメンドを再計算

実装（#12）:
- `POST /api/recipes/suggest` に `{ leftovers: [{ ingredientId, quantity }] }` を送る。画面は最良案（案 1）の余りを、冷蔵のみのもの（`perishable`）を先に並べて送る。余りがない（登録レシピが少なく案が出ない）ときはボタンを出さない
- サーバはマスタにある食材だけを名前・基準単位に直して AI に渡す（なければ 400 `UNKNOWN_INGREDIENT`）。重複回避用に登録済みレシピのタイトルを渡す
- 返った下書きは URL 取り込みと同じ `normalizeDraft` で照合・単位換算し、`sourceType = ai` で編集画面に渡す。保存またはやめると献立画面に戻り、提案を計算し直す

## プライバシー

要件「AI に渡す情報は必要最小限」に沿って、AI に渡すのは次だけにします。

- URL 取り込み: そのページの本文と、食材マスタの名前・基準単位の一覧
- 補完提案: 余りそうな食材の名前と量、既存レシピのタイトル、食材マスタの名前・基準単位の一覧
- カロリー推定: そのレシピの材料の表示文字列と人数

在庫の購入日、ミールキット、利用履歴などは渡しません。

## ウェブ検索（まとめて推定）

「分類と価格をまとめて推定」（09・10・11）で辞書・ルールで決まらず AI に回す食材の段（分類と重さ・日持ち・価格）は、AI にウェブ検索で調べさせてから答えさせます（2026-11-28 ユーザー依頼）。モデルの知識だけの答えでは、値の根拠が分からないためです。レシピの区分・系統の段は検索しません。

| provider | 検索の道具 |
|---|---|
| Cursor（Container） | `/structured` に `webSearch: true` を送ると、Container が組み込みの `webSearch`・`webFetch` を足して動かす。大きな結果は空のツリーの `/tmp` に書かれるので、それを読む `read`・`grep` も足す（ツリーは空なので、見えるのはその回の `/tmp` だけ）。シェル・書き込み・サブエージェントは今までどおり使わせない |
| Gemini（予備） | `tools: [{ google_search: {} }]`（Google Search grounding）。構造化出力と一緒に使う。考える量（`thinkingLevel: 'low'`）は付けない（low だと検索せずに答え、画像の URL を出典にした。2026-11-28 実測） |

- 切り替え: 環境変数 `AI_WEB_SEARCH`。既定は on、`off` で検索なし（今までの動き。出典は付かない）。API の `webSearch` で 1 回ごとに変えられる
- プロンプト（`src/server/ai/prompts.ts` の `PRICE_RESEARCH`・`STORAGE_RESEARCH`）
  - 日持ちは農林水産省・消費者庁・自治体・メーカー・生産者団体などの公的・一次情報を優先する
  - 価格は 2026 年の首都圏のスーパーの特売でない通常価格を優先する（総務省の小売物価統計、ネットスーパー・ネット通販の商品ページなど）
  - 根拠のページが見つからなければ null と空の `sources` を返す（推測で埋めない）
- 出典: 価格と日持ちの答えには `sources`（URL 1〜3 件）を付けさせ、`validSourceUrls()`（`src/shared/domain/sources.ts`）で確かめる。http(s) のページだけを残し、サイトのトップページ・画像などのファイル・500 文字を超える URL は捨てる。**残った出典がない答えは捨てて「答えなし」として扱う**（日持ちは今の値のまま ai、価格は未設定の印。どちらも次からは聞かない）。分類と重さは出典を保存しない
- 保存: `ingredients.price_source_urls`・`storage_source_urls`（migration 0012、URL の JSON 配列）。手で値を直したら空にする。食材の編集画面で出典のリンクを見られる
- 範囲チェック（価格 1〜20,000 円、日持ち 0〜365 日など）と、手入力（`manual`）・調べた値（`researched`）を上書きしない決まりは今までどおり
- 出典が本当に答えの根拠かまでは確かめない（URL を開いて照らし合わせることはしない）。食材の編集画面で本人が開いて確かめる

### 件数と時間

検索すると 1 回の呼び出しが遅くなるので、1 回で聞く件数（`limit`）を減らします。

| | 検索なし | 検索あり |
|---|---|---|
| `limit` の既定 | 20 件 | 5 件（`RESEARCH_ESTIMATE_LIMIT`） |
| Cursor の 1 回の上限 | 45 秒（やり直し込み 75 秒） | 4 分（やり直し込み 7 分。`RESEARCH_ATTEMPT_MS`・`RESEARCH_BUDGET_MS`。Container 側も `MAX_RESEARCH_TIMEOUT_MS` = 4 分） |
| Gemini の 1 回の上限 | 9 秒 | 2 分（`RESEARCH_TIMEOUT_MS`） |

- Workflow の step の時間切れ（10 分）に、Cursor のやり直し込み 7 分が収まる
- Workers の CPU 時間は AI の待ち時間を含まない。1 回分で使う CPU は D1 の読み書きと JSON の処理だけ（数十 ms）
- 1 つのジョブの回数の上限 `MAX_ROUNDS` を 500 にした（1 回で step を 2 つ使うので、Workflows の 1 インスタンスの step 数の上限 1,024 に収まる）。届かなければ、もう一度始めると続きから進む
- 実測（2026-11-28、Gemini `gemini-3.8-flash`、5 件）: 日持ち 33 秒・価格 28 秒、1 回あたり入力 約 600 トークン・出力 約 300〜800 トークン・考える量 約 2,000 トークン。Cursor（Container）は本物のキーがないので未実測

## 応答時間と費用

- 目標: 数十秒以内（要件）。Workers の CPU 時間は外部 API の待ち時間を含まないので問題ない
- 画面ではローディングを出し、30 秒でタイムアウト
- AI は本人がボタンを押したときだけ呼ぶ。自動では呼ばない

## カロリー推定

レシピ編集画面（S10）の「AIで推定」ボタンから呼びます。結果は `calories_kcal` に入れ、`calories_estimated = 1` として画面で「目安（AI推定）」と表示します。本人が数値を直したら `calories_estimated = 0` にします。
