# 07. 実装計画

1 PR = 1 つの機能 を目安に、上から順に積みます。各 PR は main から切り、CI（lint / typecheck / test）が通った状態で出します。

| # | PR | 内容 | 動かして確認できること |
|---|---|---|---|
| 1 | 土台 | Vite + React + Hono + Workers、Tailwind、Drizzle + D1、Vitest、GitHub Actions（CI）、タブバーの空画面、`todayJst()` | `wrangler dev` で空の画面が出る |
| 2 | デプロイ・認証 | 本番 D1、Cloudflare Access、JWT 検証ミドルウェア、main マージで export → migrate → deploy。手順書（本人が Cloudflare 画面で行う作業）を含む | スマホから空の画面が見られ、自分以外は入れない |
| 3 | DBスキーマ | 02 のテーブルとマイグレーション、ULID、共通エラー処理 | マイグレーションがローカルと本番の D1 に当たる |
| 4 | 食材マスタ | API + 画面（S12）、初期データ 50 件（目安値。1個あたりの重さ、切った後の日持ちを含む） | 食材と販売単位を登録・修正できる |
| 5 | レシピ | API + 画面（S09, S10）、単位換算（`units.ts`）、基本レシピ 10〜20 件の seed | レシピを手で登録・編集できる。seed のレシピが入っている |
| 6 | URL 取り込み | AI プロバイダ層（1 社分）、URL 取り込み（S11）、カロリー推定 | URL からレシピの下書きを作って保存できる |
| 7 | 在庫・冷蔵庫ビュー | 期限計算（純粋関数）、確保量の集計、API、画面（S02）、ホーム（S01）の期限間近 | 在庫を手で入れて期限順に見られる |
| 8 | レコメンド | `recommend.ts` と単体テスト、献立 API、画面（S03。食べる順・食数を含む） | 料理を選ぶと提案が出て確定できる |
| 9 | 買い物リスト | 生成、チェック→在庫登録、画面（S04） | 買ったものをチェックすると在庫に入る |
| 10 | 下ごしらえ・袋詰め | `prep.ts`、袋の保存場所と期限、画面（S05, S06） | 食材ごとの下ごしらえと袋の保存ができる |
| 11 | 調理 | 画面（S08）、作った・余りの更新、plan の完了、ホームの「今日はこの袋」 | 1 サイクルが最後まで回る |
| 12 | AI 補完提案 | 余りから 1 品提案（レコメンド画面から） | 余りが大きいときに AI の提案を取り込める |
| 13 | Cursor プロバイダ | Container（Node + Cursor SDK）、`CursorProvider`（[08](./08-agent.md)） | URL 取り込み・補完提案・カロリー推定が Cursor で動く |
| 14 | AI に頼む | エージェントの道具、変更案 → 確認 → 反映、画面（S13） | 「玉ねぎを半分使った」で在庫の変更案が出て、確認して反映できる |

- デプロイと認証（#2）を最初に通しておき、以降の PR は毎回スマホで確かめる
- seed のレシピ（#5）は自分で書いたもの、または AI で作って確認したもの。公式メニューの文面は写さない
- URL 取り込み（#6）を在庫やレコメンドより前に置き、レコメンドを作る時点で実データのレシピが揃っているようにする

## MVP 後（あるとよい）

- 買い物リストのオフライン（PWA、Service Worker、チェック操作のキュー）
- 調味料など常備品の管理（切れそうなときだけ買い物リストに載せる）
- 週 1 回の R2 へのバックアップ
- 設定画面（品数、期限間近の日数など。MVP では定数）
- 公式メニュー番号
- 登録レシピが 100 件を超えたら、レコメンドの候補の絞り込み

## テスト方針

| 対象 | 方法 |
|---|---|
| レコメンド、販売単位、期限、下ごしらえ集約 | Vitest の単体テスト（厚めに） |
| API | `@cloudflare/vitest-pool-workers` でローカル D1 を使った結合テスト（主要な流れ） |
| AI | FakeProvider で流れだけテスト。実プロバイダは手動確認 |
| 画面 | MVP では手動確認。1 サイクル通しの E2E（Playwright）は余裕があれば追加 |
